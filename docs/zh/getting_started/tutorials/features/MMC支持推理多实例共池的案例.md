# MemCache 支持推理多实例共池的案例

[TOC]

## 1. 场景

在线推理通常会部署多个实例，但很多请求前缀其实高度重复，比如 system prompt、RAG 模板、few-shot 示例。

问题在于：如果每个实例都各算各的，同一份前缀会被反复 prefill。算力烧了，TTFT 还高，这不划算。

## 2. 怎么做

- **多个推理实例接入同一个 MemCache 池，即用同一个MetaService来管理想要共池的所有LocalService实例。**
- MetaService 管理元数据和池空间。
- LocalService 提供 DRAM/HBM 内存池。
- 同机共享可走 `host_shm`，跨机共享可走 `device_rdma`、`device_sdma`、`host_rdma`。

核心观点很明确：MemCache 不是给每个实例再塞一个私有缓存，而是把 `KVCache` 变成整个实例池都能复用的公共资产。

```text
                +-------------------+
请求1 ----------> 推理实例 A        |
请求2 ----------> 推理实例 B        |-----> 共享 MemCache 池
请求3 ----------> 推理实例 C        |         (KV blocks)
                +-------------------+

未命中: 实例自己 prefill 后写入池
命中:   其他实例直接读共享 KV，跳过重复 prefill
```

## 3. 请求怎么走

1. 实例先按“模型 + 前缀 + 版本”生成 KV key。
2. 命中 MemCache：直接读取共享 KV，继续增量计算。
3. 未命中 MemCache：当前实例执行 prefill，再把 KV 写回共享池。
4. 后续同前缀请求落到任意实例，都能复用这份 KV。

## 4. 结果

- 多实例共池，不再各自囤一份热点 KV。
- 数据共享，把单实例私有状态变成实例池公共状态。
- TTFT 下降，因为最重的 prefill 被复用了。

只要业务里有稳定的前缀复用，做 KV 共享就是对的；如果每个请求前缀都完全不同，那收益就会迅速变薄。
